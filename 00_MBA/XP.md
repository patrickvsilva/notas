eXtreme Programming (final dos anos 1990): **composição** de valores, princípios e práticas — as práticas **já existiam**; o XP as arranjou num desenho que difere do tradicional. Sem esse desenho, a prática isolada não se entende.

## Ideia Central
Ágil é atitude ([[Métodos Ágeis]]); XP é o pacote técnico. Quatro **valores** orientam as práticas:

| Valor | Em uma linha |
|---|---|
| Feedback | cliente é **produtor e consumidor**, o tempo todo — ciclo até ficar satisfeito |
| Comunicação | conversa > documento; doc registra o **já feito**; o a fazer vai no cartão de estórias |
| Simplicidade | só o pedido; especular **com** o cliente; objetivo = evitar retrabalho |
| Coragem | adotar o XP contra o processo tradicional (lista abaixo) |

**Feedback** — cliente lança ideia → equipe altera o software → mostra → repete. Para quando o cliente está satisfeito. Proximidade reduz erro de interpretação.

**Comunicação** — ligada ao feedback; o canal (face a face, telefone, etc.) muda a compreensão. Explicar o que fazer é **interativo** ([[História de Usuário|cartão de estórias]]), não um spec prévio.

**Simplicidade** — ações simples → feedback rápido (cliente entende). Não assumir necessidade futura: **pergunte**. Ex. (Fabri): modelar “cidade” por precaução — fez várias vezes e **nunca** usou.

**Coragem** — o XP contraria o tradicional. Exige coragem para: (1) evoluir; (2) manter simples; (3) cliente prioriza; (4) pares; (5) refactoring; (6) testes automatizados; (7) estimar estórias **com** o cliente; (8) código visível a todos; (9) integrar várias vezes ao dia; (10) ritmo sustentável; (11) largar doc-defesa; (12) contrato de **escopo variável**; (13) propor o processo ao time.

Práticas (se sustentam em conjunto; isolada não é XP):

| Prática                   | Em uma linha                                                               |
| ------------------------- | -------------------------------------------------------------------------- |
| Planejamento constante    | pode ir ao papel; não congela por meses                                    |
| Proximidade com o cliente | cliente **no time**, não só no contrato                                    |
| Design simples            | simplicidade e elegância — o suficiente **agora** ([[Design de Software]]) |
| Metáfora                  | vocabulário compartilhado do sistema                                       |
| Código coletivo           | qualquer um altera qualquer parte                                          |
| Refatoração               | melhorar design sem mudar comportamento                                    |
| Stand-up                  | sync curto do time                                                         |
| TDD                       | teste **antes** do código de produção                                      |
| Padrões de código         | convenção do time — **não** é [[Padrões de Projeto]] (GoF)                 |
| Pair programming          | dois no mesmo código (review contínuo)                                     |

Por isso o professor insiste no XP **como projeto**, não numa prática “incorporada”.

## Quando
- **Usar:** time que precisa de disciplina **técnica** (TDD, pares, refatoração) e cliente no time; combina com [[Scrum]] na gestão do fluxo.
- **Evitar:** puxar uma prática e achar que é XP; só stand-up; especular sem o cliente; ou documentação que descreve o *a fazer* no lugar do cartão de estórias.
